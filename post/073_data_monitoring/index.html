Data Pipeline Observability

Translating Google’s SRE framework to data pipelines — and the platform bet that delivers them for free

The Question

A data platform team at any reasonably mature org owns thousands of pipelines and thousands of tables. Sooner or later, someone has to answer:

For every job and every table, how much data did this run touch, how long did it take, how much did it cost — and how does that compare to yesterday, last week, last month?

Sounds boring. It’s the highest-leverage question a platform team can answer, because almost every silent data-pipeline failure shows up first as a change in one of those numbers.


The Four Golden Signals, Translated to Data Pipelines

Google’s SRE book defines the Four Golden Signals — latency, traffic, errors, saturation — as the minimum any user-facing service should monitor. All four matter just as much for data pipelines.

Errors are the easy one. A failed job throws an exception, the orchestrator (Airflow, ADF, etc.) catches it, an alert fires, an engineer reads the logs.

The other three are the hard ones. None of them surface as exceptions; they only show up if something is actively measuring them per job, per run, at scale.

1. Traffic — Rows and Bytes, In and Out

Google defines traffic as “a measure of how much demand is being placed on your system.” For a pipeline, demand is data volume — rows and bytes flowing through each input and output, tagged by source, direction, and user.

Compared run-over-run, this is the highest-signal data observability metric. A job that succeeds while reading half as much data as yesterday is almost certainly broken upstream — and no exception, no exit code, no SLA breach catches it. The job finishes, but it just doens’t do what it’s supposed to do.

2. Latency — Job Duration vs Historical Baseline

For a pipeline, latency is total job runtime. Like latency for a user-facing service, it’s only meaningful relative to its own history. A job that always takes 30 minutes is fine taking 30 minutes; a job that suddenly takes 60 is alarming.

What this catches: slow regressions from data growth, regressions after a code change that broke partition pruning, and infrastructure-shaped issues distinguished from data-shaped issues.

3. Saturation — CPU, Memory, Spill, GC

Google defines saturation as “how full your service is, emphasizing the resources that are most constrained.” For Spark, that’s stage-level resource metrics — executor run time, CPU time, memory and disk spill, JVM GC time — for every stage of every job.

This turns “this job is slow” into “stage 7 is GC-bound” or “executors are blocked on disk spill”.


How to Monitor at Scale

The harder question is: how do we actually produce them at scale, for every job, without an instrumentation cost?

Take traffic for example. The two obvious answers don’t survive contact with reality.

“Just schedule a cron ETL that counts rows in each table.”

The naive answer: a separate, scheduled job that runs SELECT COUNT(*), SUM(<byte_size>) FROM <table> against every table we care about.

  • Doesn’t scale to thousands of tables. Every new table is one more entry to maintain.
  • Costs real compute. Each count is a full scan, every hour, against every table. That bill isn’t free.
  • Lags behind reality. By the time the counter runs, the upstream job finished hours ago. We can’t attribute a 30% drop to a specific run of a specific job.
  • Doesn’t tell who wrote what. A row count on a table doesn’t tell which job produced those rows or what it read to produce them.

“Just ask each user to add df.count() after every write.”

The other obvious answer: push instrumentation down to the user. Adopt a convention — “after every write, add a line that counts and reports.”

  • Optional instrumentation is forgotten instrumentation. In a platform with hundreds of contributors, “every team should remember to do X” is a hope, not a strategy.
  • df.count() isn’t free. It can re-trigger work unless the user caches first. Now we’re asking every user to think about caching too, which they’ll get wrong.
  • It’s inconsistent. Two teams tag their metrics differently and we can’t compare them.

Both fail for the same reason: they push observability work onto the people consuming the platform, instead of making it a property of the platform itself.


What I Built

The library I built takes a different angle. The library hooks into Spark’s runtime internals and collect every signal we want — bytes read per scan, rows written per output, CPU time, GC time, spill per stage.

The integration is a single object, instantiated once at application start:

implicit val spark: SparkSession = SparkSession.builder()
  .appName("my-job")
  .getOrCreate()

val observability = new PlatformObservability(
  metricPrefix = "platform.spark.observability",
)(spark)

observability.register()

Under the hood, it attaches to Spark’s runtime and collects the metrics that matter. Metrics are pushed async to a metrics gateway and visualized in Grafana, where the baselines, alerts, and per-team dashboards live.

No df.count(). No per-team convention. No extra Spark actions. No extra compute.


Beyond the Monitoring: Optimization Hints

The library also runs a small heuristic: if the same DataFrame shows up without an intervening .cache() or .persist(), the metrics is sent. That’s the most common reason a Spark job costs twice what it should.

With this metric, a dashboard can list the jobs with duplicate-compute warnings, and an engineer can fix them for real cost savings. Without it, those jobs stay broken for years.


Integration: One Line, Zero Overhead

What does a team using this library actually pay for it?

  • One line of code. The whole user-facing API is installing the library.
  • Zero per-job compute overhead. The library collect the metrics from Spark internals for free!
  • Standard. The platform owns the library; the user gets the signals.

The Result: A Real Incident

A daily pipeline of ours once finished one morning with every signal green — exit code zero, all stages succeeded, alerts silent — but had quietly written only ~40% of its usual output rows. An upstream feed had degraded overnight. The data team didn’t catch it. A business user did, hours later, when the revenue dashboard came in well below baseline.

The library catches that class of failure now. The moment output volume deviates from its rolling baseline, the alert fires.


What’s Next

  • Freshness / SLA. “Is this table up to date relative to its contract?” The runtime can tell you a job ran; the orchestration and data-contracts layer has to tell you the table should have been ready by 9 AM.
  • Data quality. Schema drift, null rates, distribution checks, business-rule violations — and where they belong in the stack (Great Expectations, Deequ, dbt tests) versus what the runtime layer already catches.
  • Lineage. The library already captures which sources each job read and wrote. The next step is shipping that to a catalog/lineage layer (OpenLineage, Unity Catalog) to build the cross-job graph the platform team actually needs.
